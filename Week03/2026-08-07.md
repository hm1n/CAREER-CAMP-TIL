## 오늘 배운 내용

#### 📌 설계가 변경될 때, 변경 이력과 근거를 정리하기

구현 과정에서 처음에 정의한 설계서의 내용과 달라졌을 때, 설계서의 내용이 변경된 이력과 근거에 대해 정리하는 방법에 대해 고민해볼 수 있었다. 오늘은 일회성으로 끝나는 작업이기 때문에 설계서 문서 자체를 업데이트하는 방식으로 끝내긴 했지만, 만약 다른 프로젝트나 실무에 적용한다면 원문을 수정하기 보다는 기존 문서는 outdated로 표기하고 새 문서를 만든다던가 하는 방식을 사용할 수 있을 것 같다고 생각했다. 그리고 이번 기회로 더더욱 LLM 위키의 필요성에 대해 느낄 수 있었다.

#### 📌 LLM 위키 적용 방법

LLM 위키를 적용하는 가이드라인 파일을 받아서 정독하고 앞으로 적용 계획에 대해 정리해보았다. LLM 위키의 폴더 구조, 각 폴더와 파일의 역할, 좋은 문서를 작성하는 방법 등 여러 개념적인 내용에 대해 알 수 있었고 앞으로 어떻게 적용하면 될 지 가닥을 잡을 수 있었다.

## 더 알아보고 싶은 것

#### ❓ LLM 위키와 다른 문서를 구분하는 방법

LLM 위키 외에도 Github PR, Issue와 노션을 병행해서 정리하고 있는데 역할의 구분이 애매해지는 것 같다. 내 생각엔 Github 문서와 노션 문서는 다른 사람에게 공유하는 용도이기 때문에 LLM 위키에서 `/output` 에 해당하는 개념이 될 것 같은데, 이 방식이 맞을지는 직접 적용해보면서 느껴보려고 한다.

#### ❓ LLM 위키를 프로젝트 외에 적용할 수 있는 영역

문서에서는 실습 예제로 간단한 업무 자동화를 예시로 들고 있는데, 이 예시를 보고 프로젝트 외에 다른 영역에도 LLM 위키를 적용할 수 있다는 생각을 처음으로 하게 됐다. 내가 하고 있는 프로젝트 외의 것들(문서화, 자동화, 취업 준비 등)에 어떻게 적용할 수 있는지는 일단 프로젝트에 적용해보고 직접 느껴본 후에 생각하는 게 좋을 것 같다. 한 번 써 보면 쓸 수 있는 다른 곳들이 분명 보일 거다.

## 나에게 적용한다면

#### 💡 크게 말고 당면한 이슈부터 주제로 잡고 LLM 위키 만들기

이미 내 사이드 프로젝트는 많이 진행된 만큼 그동안의 모든 맥락과 내용을 LLM 위키로 병합할 수는 없다. 애초에 LLM 위키는 작게 시작해야 한다고 강조하고 있기도 하다. 그래서 크게 구조를 잡을 생각은 하지 말고, 당면한 작은 이슈(E2E 테스트 도입)부터 적용해보고 조금씩 개선해나가려고 한다.

#### 💡 SEO 개선 4주 프로젝트에도 LLM 위키 적용해보기

SEO 개선, GEO 도입 등 앞으로 한달 간 진행할 수치 개선 과정에도 LLM 위키를 적용해보면 좋을 것 같다. 어차피 같은 프로젝트니 일단 디렉토리 만드는 것부터 시작해 보자.
